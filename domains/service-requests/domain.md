# Service Requests Domain

## Responsibility

This domain manages repair requests from creation to closure. It records request details, lifecycle status, clarification needs, assignment metadata, and status history.

## Initial Statuses

- `new`
- `needs_clarification`
- `awaiting_assignment`
- `technician_assigned`
- `visit_scheduled`
- `diagnostics`
- `waiting_for_parts`
- `repair_in_progress`
- `completed`
- `closed`
- `warranty_case`
- `cancelled`

## First Use Cases

- Create repair request.
- Generate public request number.
- Add status event.
- Ask clarification question.
- Record customer answer.
- Assign technician manually.
- Show public status page data.

## Phase 02 Intake Model

The first persisted intake flow creates a service request in status `new` from a public form. The service-request domain owns the public request number, lifecycle status, problem description, district or address, urgency, and attachment metadata links.

Public request numbers use the format `CFX-YYYYMMDD-000001`, where the date is generated by the API and the sequence is local to the current persistence store.

Required intake fields:

- Customer name and phone.
- Customer client type: `private`, `office`, `coffee_shop`, `restaurant`, or `other`.
- Machine brand and location type.
- Problem description.
- District or address.
- Urgency: `today`, `one_two_days`, or `planned`.

Optional intake fields:

- Telegram handle.
- Machine model.
- Attachment metadata: filename, content type, and byte size.
